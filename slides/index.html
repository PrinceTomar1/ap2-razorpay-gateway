What AP2 fixes

A purchase carries a mandate, not a credential.

A signed, constrained, verifiable statement of what the buyer actually authorised — checked by every party in deterministic code before money moves.

The agent can shop. It cannot pay. It holds a keypair and no money — every purchase is a closed mandate under the buyer’s standing authorisation, and the verifier checks it before a rupee moves.

The load-bearing decision

“When this document refers to validation or processing for a particular role, it MUST happen in deterministic code — regardless of whether the role is agentic or not.” AP2 v0.2 · docs/ap2/specification.md
$ grep -rn "anthropic\|reason(" gateway/verify.py gateway/payments.py gateway/recovery.py $ echo $? 1 ← empty. and that grep is a test.

A verifier is a classifier over a small, fully specified domain. Does this signature check out. Is this integer below that integer. Code does that perfectly and explains what it compared. A model does it probabilistically, can’t be audited afterwards, and adds a network dependency to the one path that must never be down.

Two orders. One capture.

Nothing charged twice.

Idempotency key is sha256(payment_mandate.id). Before creating that second order it asks the rail whether the first one captured — because the dangerous case in payments isn’t a decline, it’s a timeout, where you don’t know whether the money moved.

Edit a payload, edit a reason, delete a row, reorder two, re-hash a row and forge its link, splice one in — each is caught and the damaged row is named. The tests drop the database’s append-only triggers first, because a tamper-evidence claim you haven’t tried to break is a hope, not a property.
